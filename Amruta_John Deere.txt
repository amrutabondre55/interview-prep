Liskov Substitution Principle — Simple interview definition
LSP says that a child class should be replaceable with its parent class without breaking the program.
Bird example
The problem is: not every bird can fly, so fly() should not be forced into the Bird class.
Use an interface for flying birds:
interface Fly {
    void fly();
}

class Bird {
    void eat() {
        System.out.println("Bird is eating");
    }
}

class Sparrow extends Bird implements Fly {
    @Override
    public void fly() {
        System.out.println("Sparrow is flying");
    }
}

class Penguin extends Bird {
    // Penguin cannot fly
}

public class Main {
    public static void main(String[] args) {

        Bird sparrow = new Sparrow();
        Bird penguin = new Penguin();

        sparrow.eat();   // Works
        penguin.eat();   // Works

        // Only Flyable birds can fly
        Flyable flyingBird = new Sparrow();
        flyingBird.fly();

        // This would NOT compile:
        // Flyable penguin = new Penguin();
		}
	}
	What is happening?
	Bird
	 ├── Sparrow → can eat + fly
	 └── Penguin → can eat

	Flyable
	 └── Sparrow
	Because Penguin is a Bird, we can safely use:
	Bird bird = new Penguin();
	bird.eat();
	But we don't claim every Bird is Flyable.
	Interview explanation
	You can say:
	"For example, Sparrow and Penguin are both Birds, but only Sparrow can fly. If I put fly() in the Bird class, Penguin would inherit a behavior it cannot support, which violates LSP. So I keep common behavior in Bird and use a Flyable interface for birds that can fly. This allows each subclass to be safely substituted where its parent type is expected."
	Easy memory trick:
	LSP = "Child should be safely replaceable for Parent."

StringBuffer vs String Builder
StringBuffer → Thread-safe → Synchronized → Slower
StringBuilder → Not thread-safe → Not synchronized → Faster
Both StringBuffer and StringBuilder are mutable classes used to modify strings efficiently. The main difference is that StringBuffer 
is synchronized and thread-safe, whereas StringBuilder is not synchronized and is not thread-safe. Because StringBuilder doesn't 
have synchronization overhead, it is generally faster and is preferred in single-threaded scenarios. StringBuffer can be used 
when thread-safe operations are required.

->StringBuilder
	StringBuilder is used to create and modify strings without creating a new String object every time.
	It is not synchronized, so it is faster.
	Use it when: Working in a single-threaded environment
				-You need frequent String modifications
				-Performance is important

- StringBuffer
	StringBuffer is also mutable, but its methods are synchronized.
	Because it is synchronized, it is thread-safe, but generally slower than StringBuilder.
	Use it when: Multiple threads may access the same StringBuffer
				-You specifically need thread-safe String modification
				
1. Use String when the value doesn't change -> You don't continuously modify employeeName, so String is appropriate.
2.Use StringBuilder for frequent modifications.-> Suppose you're building a large String: Use StringBuilder when: You are repeatedly 
				using append(), insert(), delete(), etc.- The code is mainly single-threaded -You want better performance.
Real project example: If I need to dynamically build a SQL query, log message, CSV row, or response String inside a single request/thread, I would generally use StringBuilder.
3. Use StringBuffer when thread safety is required.

I use String when the value is not frequently modified because String is immutable. If I need frequent String modifications 
in a single-threaded scenario, I use StringBuilder because it is mutable and faster. If the same mutable String object needs 
to be safely accessed and modified by multiple threads, I use StringBuffer because its methods are synchronized.

characteristics :-The main characteristics of REST are statelessness, client-server architecture, uniform interface, resource-based URLs, proper HTTP methods and status codes, cacheability, and layered architecture.

Q2)why is stateless important? 
->“Statelessness means the server does not store the client's session state between requests. Each request must contain all the information required to process it.
It is important because it makes the application easier to scale. For example, if we have multiple backend servers behind a load balancer, any request can go to any server because the server does not depend on previous requests.
It also improves reliability because if one server goes down, another server can process the next request without losing the client's session state.

example:-	For authentication, instead of storing session information on the server, we can use a JWT token. The client sends the token with every request, so any server can validate it.”
Stateless APIs are also easier to cache, monitor, and deploy.

Q3)what challenges does statelessness create? 
-Although statelessness provides scalability, it also creates some challenges.
-First, every request needs to contain the required context, such as authentication information, which can increase the request size.
-Second, we cannot rely on server-side session state, so things like shopping carts or temporary user information need to be stored in an external system such as Redis or a database.
-Third, repeated authentication and data retrieval can increase processing overhead.
Finally, designing workflows that depend on previous requests can be more complex because the server doesn't remember the previous request.
-Strong closing line:-	So, statelessness improves scalability, but we usually move required state to external systems such as databases or distributed caches.

Q4)difference between PUT and PATCH. 
->Both are HTTP methods used to update a resource, but the main difference is how much data you send.
->PUT is generally used to replace the complete resource, while PATCH is used to partially update specific fields.
->For example, suppose an employee has name, email, department, and salary. With PUT, I would generally send the complete employee representation. With PATCH, I could send only the department that needs to be changed.
->PUT is also considered idempotent, meaning sending the same request multiple times should result in the same final state. PATCH can be idempotent depending on how the API operation is designed.

Q5) what is N+1 problem? 
The N+1 problem happens when we load a list of parent entities and then trigger one extra query per parent to fetch its children, causing too many queries and slowing down the application. For example, looping through 100 orders and triggering 100 more queries for items. We can solve this by using fetch join or entity graphs to load the needed data in fewer queries.” Quick trick: If you see a parent loop plus lazy loaded children, think N+1.

// The N+1 problem is a database performance issue that commonly occurs when using ORM frameworks such as Hibernate or JPA.
It happens when the application executes one query to retrieve a list of parent records and then executes an additional query for each parent record to retrieve related data.
For example, if I fetch 100 orders using one query and then Hibernate executes another query for each order to fetch its order items, we end up with 101 queries. That's why it is called the N+1 problem.
This can significantly increase database calls and API response time.

Q. How to identify errors client-side versus server-side? 
->I identify client-side and server-side errors mainly based on the HTTP status code and the error response.
->4xx errors generally indicate a problem with the client request. For example, 400 Bad Request means invalid input, 401 means authentication is required, and 404 means the requested resource was not found.
->5xx errors indicate a problem on the server side. For example, 500 Internal Server Error means an unexpected error occurred while processing the request.
->To troubleshoot, I first check the browser or API client response, request parameters, and payload for 4xx errors. For 5xx errors, I check application logs, stack traces, database connectivity, and downstream services.
So, in simple terms, 4xx usually means the client request has a problem, while 5xx usually means the server failed while processing a valid request.

4xx → Client/request problem
5xx → Server/application problem

Q What is vulnerability? What is OKTA? 
-A vulnerability is a weakness or security gap in an application that can be exploited by an attacker. For example, SQL injection, weak authentication, exposing sensitive data, or missing authorization checks can create vulnerabilities.
-In API security, I try to prevent vulnerabilities by using input validation, authentication and authorization, HTTPS, secure token handling, rate limiting, and proper error handling.

What is OKTA?
Okta is an identity and access management platform(IAM). It can be used for user authentication, single sign-on, and authorization.
Think of Okta as a central identity provider between the user and your applications.
In a REST API architecture, Okta can act as an authorization server. The client authenticates with Okta and obtains an access token. The client then sends that access token to the API, and the API validates the token and checks the required scopes or permissions before allowing access.

Vulnerability = Security weakness
Okta = Identity + Authentication + Authorization

Q what do you secure REST API? 
-I would secure REST APIs using authentication, authorization, HTTPS, input validation,Rate limiting token validation, and proper error handling.
->I secure REST APIs using multiple layers of security.
First, I use HTTPS to encrypt communication between the client and server.
Second, I implement authentication, for example using OAuth 2.0 and JWT access tokens.
Third, I implement authorization using roles and scopes, so authenticated users can only access resources they are permitted to access.
I also validate request inputs to prevent attacks such as SQL injection, apply rate limiting to prevent abuse, and use secure error handling so sensitive information is not exposed.
Finally, I use short-lived tokens, secure secret management, logging and monitoring, and proper security headers where applicable.

Authentication answers ‘Who are you?’, while authorization answers ‘What are you allowed to do?’”
In Spring Boot, Spring Security can be used to implement authentication and authorization.

Q A client starts sending 1000 requests per minute. 
If one client suddenly starts sending 1000 requests per minute, I would first determine whether this is legitimate traffic or abnormal behavior.
I would check API metrics, logs, client identification, endpoint usage, and request patterns.
-If the traffic exceeds the allowed limit, I would apply rate limiting or throttling at the API gateway or application level. For example, I 
could allow a specific number of requests per minute and return 429 Too Many Requests when the limit is exceeded.
-I would also investigate why the client is generating so many requests. It could be a retry loop, a bug, or potentially abusive traffic.
-I would monitor the API's CPU, memory, database connections, and latency to make sure the high traffic isn't affecting other clients.
If necessary, I would temporarily block or restrict the client and then fix the underlying issue.

⭐ Important

1000 requests/minute doesn't automatically mean an attack.

First:

Identify → Analyze → Rate Limit → Monitor → Investigate

Rate limiting is also important for protecting APIs from excessive resource consumption and availability issues.

Q API gateway. What is an API gateway and what role does it play in API management? Discuss its benefits and potential drawbacks. 
->“An API Gateway is a single entry point between clients and backend services, especially in a microservices architecture.

Instead of the client directly communicating with multiple microservices, the client sends requests to the API Gateway, and the gateway routes those requests to the appropriate service.

It can also handle common concerns such as authentication, authorization, rate limiting, throttling, request routing, logging, monitoring, and sometimes load balancing or request transformation.

The main benefits are centralized security, simpler client communication, consistent policies, and reduced duplication across microservices.

The potential drawback is that if the gateway is not properly designed and scaled, it can become a bottleneck or a single point of failure. It also adds another network hop and another component to maintain.
API Gateway = Single Entry Point + Routing + Security + Rate Limiting
